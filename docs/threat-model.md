# MedCore STRIDE threat model

## Scope and trust boundaries

Clients cross the HTTP/API boundary with a bearer token or, on refresh, an HttpOnly cookie. Stripe crosses a dedicated raw-webhook boundary with a signed body. The API and BullMQ worker share MongoDB, Redis, and application configuration. MongoDB stores domain state and ciphertext. Redis stores leases, rate windows, and job state. KEKs and the Ed25519 private key are application-side secrets, and the anchor store is outside MongoDB.

| STRIDE                 | Threat and target                                                              | Implemented mitigation                                                                                                                                                                                                          | Residual risk or operational control                                                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Spoofing               | Stolen credentials, forged JWT or Stripe webhook                               | Argon2id password hashing, HS256 algorithm restriction and 15-minute access tokens, opaque hashed refresh tokens with rotation and family reuse revocation, Stripe signature verification on raw bytes                          | Protect JWT and webhook secrets. An issued access JWT remains valid until expiry. TLS is required for deployment.                                                   |
| Tampering              | Concurrent or replayed booking, changed prescriptions, rewritten audit records | Redis token-owned lease, atomic MongoDB availability update and partial unique appointment index, payload-bound user-scoped idempotency, AES-GCM tags with appointment/patient AAD, linked audit hashes and Ed25519 checkpoints | Protect anchor storage and keys independently. The interval after the newest anchor is not independently checkpointed.                                              |
| Repudiation            | Denial of a booking confirmation or prescription creation                      | Audit entry written with the business mutation, sequence and hash verification, signed checkpoints, request IDs in structured logs                                                                                              | Application-held keys attest to the checkpoint. Individual user non-repudiation and complete coverage of all actions require additional controls.                   |
| Information disclosure | Prescription data, refresh tokens, secrets, operational information            | Encrypted prescription fields, wrapped DEKs, hashed refresh tokens, HttpOnly and SameSite cookies with Secure in production, no raw audit payload, metadata-only request logs, ownership checks                                 | Identifiers and operational metadata remain visible to database or metrics readers. Restrict network and secret-store access, particularly for metrics and backups. |
| Denial of service      | Login brute force, slot hot spots, Redis failure, repeated webhooks            | Sliding-window limits and tighter login limit, Redis fast rejection, bounded Redis commands, MongoDB fallback, webhook deduplication and background retries                                                                     | Redis outages disable application rate enforcement. Upstream limits, capacity monitoring, and recovery tests are deployment controls.                               |
| Elevation of privilege | Patient accesses another prescription or obtains staff privileges              | Public registration creates patients only. JWT roles, route RBAC, prescription/booking ownership checks, admin-only key rotation and anchoring                                                                                  | Protect privileged accounts and operational role provisioning. A role change takes effect as access tokens expire or are replaced.                                  |

## Data protection and GDPR notes

The audit collection stores payload hashes instead of raw patient data. Prescription medical fields are encrypted, while appointment, patient, and doctor references remain linkable data. Treat logs, database backups, outbox/inbox payloads and signed checkpoints according to their actual contents and access paths.

Retention, erasure workflows, access reviews, key custody, backups and incident response depend on the deployment and data controller's policies. The repository's controls do not establish GDPR compliance on their own.
